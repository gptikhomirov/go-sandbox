# Мой текущий прогресс

## Уже пройдено

### Практика 1 — базовое чтение и фильтрация

Ключевые слова:

```sql
SELECT
FROM
WHERE
AND
OR
NOT
IN
NOT IN
BETWEEN
ORDER BY
ASC
DESC
LIMIT
```

Также пройдено:

```sql
=
<>
>
<
>=
<=
```

Важные правила:

* строки пишутся в одинарных кавычках: `'Berlin'`;
* двойные кавычки в PostgreSQL — для имён колонок/таблиц;
* несколько колонок пишутся без скобок:

```sql
SELECT id, name, age
```

а не:

```sql
SELECT (id, name, age)
```

---

### Практика 2 — NULL, LIKE / ILIKE

Ключевые слова:

```sql
IS NULL
IS NOT NULL
LIKE
ILIKE
```

Важные правила:

* `NULL` проверяется только через `IS NULL` / `IS NOT NULL`;
* нельзя писать `email = NULL`;
* `LIKE` — поиск с учётом регистра;
* `ILIKE` — поиск без учёта регистра в PostgreSQL;
* `%` означает любое количество символов.

---

### Практика 3 — агрегаты и группировка

Ключевые слова:

```sql
COUNT
SUM
AVG
MIN
MAX
GROUP BY
HAVING
FILTER
```

Важные правила:

* `COUNT(*)` — preferred для подсчёта строк;
* `COUNT(column)` считает только не-NULL значения;
* если в `SELECT` есть обычная колонка + агрегат, обычная колонка должна быть в `GROUP BY`;
* `WHERE` фильтрует строки до группировки;
* `HAVING` фильтрует группы после группировки;
* в PostgreSQL лучше не использовать alias из `SELECT` внутри `HAVING`, лучше повторить агрегат;
* `FILTER` используется для условных агрегатов:

```sql
COUNT(*) FILTER (WHERE is_active)
```

---

### Практика 4 — изменение данных

Ключевые слова:

```sql
INSERT
VALUES
UPDATE
SET
DELETE
RETURNING
```

Важные правила:

* `UPDATE` и `DELETE` почти всегда должны иметь `WHERE`;
* `RETURNING` в PostgreSQL нужен, чтобы сразу вернуть созданные/изменённые/удалённые данные;
* для boolean в PostgreSQL нормально писать:

```sql
WHERE is_active
```

и:

```sql
WHERE NOT is_active
```

* production-style state transition:

```sql
UPDATE orders
SET status = 'paid'
WHERE id = $1
  AND status = 'pending'
RETURNING id, status;
```

То есть обновляем не только по `id`, но и проверяем текущее состояние.

---

### Практика 5 — простые связи и транзакции

Сейчас нужно добить:

```sql
JOIN
LEFT JOIN
ON
JOIN + GROUP BY
BEGIN
COMMIT
ROLLBACK
```

`BEGIN / COMMIT / ROLLBACK` уже базово поняты.

Нужно закрепить:

* разницу `JOIN` и `LEFT JOIN`;
* `LEFT JOIN + WHERE joined_table.id IS NULL`;
* `LEFT JOIN + COUNT(o.id)`;
* фильтрацию правой таблицы в `ON`, если нужно сохранить все строки слева;
* `JOIN + GROUP BY`;
* почему после `LEFT JOIN` нельзя бездумно использовать `COUNT(*)`.

# Production-style правила для JOIN

Всегда предпочитай алиасы таблиц:

```sql
FROM users u
JOIN orders o ON o.user_id = u.id
```

В `SELECT`, `WHERE`, `ON`, `GROUP BY` указывать колонки явно:

```sql
u.id
u.name
o.id
o.status
o.amount
```

Не писать просто:

```sql
id
name
status
```

если есть несколько таблиц.

---

## JOIN

`JOIN` возвращает только строки, где связь есть.

```sql
FROM users u
JOIN orders o ON o.user_id = u.id
```

Если у пользователя нет заказов — он не попадёт в результат.

---

## LEFT JOIN

`LEFT JOIN` возвращает все строки из левой таблицы, даже если справа связи нет.

```sql
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
```

Если у пользователя нет заказов, поля `o.*` будут `NULL`.

---

## Паттерн: найти записи без связи

```sql
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL
```

Это означает: пользователи, у которых нет заказов.

---

## Паттерн: посчитать связанные записи, включая 0

Нужно:

```sql
COUNT(o.id)
```

а не:

```sql
COUNT(*)
```

Потому что после `LEFT JOIN` пользователь без заказов всё равно даёт одну строку, и `COUNT(*)` может вернуть 1.

---

## Паттерн: посчитать только paid-заказы, сохранив всех пользователей

Preferred-вариант:

```sql
FROM users u
LEFT JOIN orders o
  ON o.user_id = u.id
 AND o.status = 'paid'
```

Потом:

```sql
COUNT(o.id)
```

или:

```sql
COALESCE(SUM(o.amount), 0)
```

# Как проверять мои ответы локально

Когда я присылаю SQL:

1. Выполни мой запрос в PostgreSQL.
2. Покажи, выполняется ли он синтаксически.
3. Покажи результат запроса.
4. Объясни, соответствует ли он задаче.
5. Покажи preferred production-style вариант.
6. Объясни только важные отличия.
7. Не перегружай теорией, если ошибка простая.
8. После проверки дай следующую задачу только если текущая тема усвоена.

Для `SELECT` можно выполнять напрямую.

Для `INSERT`, `UPDATE`, `DELETE` во время обучения лучше делать так:

```sql
BEGIN;

-- мой запрос

ROLLBACK;
```

если задача явно не требует `COMMIT`.

Перед каждой новой практикой можно сбрасывать seed data, чтобы результаты были предсказуемыми (через `docker compose down -v && docker compose up -d` в `sql/`).
