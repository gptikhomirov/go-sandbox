# Топ-100 задач бэкендера по частоте

Сортировка: **как часто эта задача прилетает как тикет в Jira** за карьеру бэкендера на типовых веб-сервисах.

## Топ-10 — задеваются почти каждой фичей

1. **CRUD-эндпоинт** на новый ресурс (создать/прочитать/обновить/удалить)
2. **Добавить поле** в существующий ресурс (миграция + DTO + валидация)
3. **Валидация входных данных** — типы, обязательность, длина, диапазоны
4. **Корректные HTTP-коды и формат ошибок** — 400 vs 404 vs 409 vs 422
5. **Структурированное логирование** запросов и ошибок (с request-id)
6. **Пагинация** списков (`?limit=20&offset=…` или cursor)
7. **Фильтрация** по query-параметрам (`?status=active&author_id=…`)
8. **Сортировка** по полям (`?sort=-created_at`)
9. **Поиск по подстроке** (`WHERE name ILIKE '%...%'`, потом full-text)
10. **Авторизация на уровне ресурса** — «может ли *этот* юзер читать/менять *эту* запись», а не просто «залогинен ли»

## 11–20 — раз в спринт точно

11. **Миграция БД** — добавить таблицу/колонку/индекс через миграционный инструмент (goose, migrate)
12. **Транзакция БД** — несколько изменений должны произойти все вместе или ни одно
13. **JOIN'ы и связи** — one-to-many, many-to-many через связующую таблицу
14. **Индекс под медленный запрос** — снять `EXPLAIN`, добавить индекс, перепроверить
15. **Даты и таймзоны** — хранить в UTC, отдавать в ISO 8601, парсить вход
16. **Деньги** — хранить в decimal или копейках, никогда не во float
17. **Аутентификация** — логин по email/паролю, выдача токена (пишется ~раз в проект, но всё ещё частая)
18. **Health-check / readiness** — эндпоинт `/health`, чтобы k8s знал, жив ли сервис
19. **Загрузка/отдача файлов** — multipart upload, лимит размера, отдача через signed URL
20. **CORS-настройки** — чтобы фронт с другого домена смог стучаться

## 21–50 — раз в месяц-два

21. **Soft delete** — колонка `deleted_at` вместо физического удаления
22. **Bulk-операции** — вставить/обновить 1000 строк одним запросом, а не циклом
23. **N+1 запросов** — отдельный тикет «список грузится 3 секунды»; чинится `JOIN` или batch-load
24. **Кеширование тяжёлого ответа** в Redis с TTL
25. **Инвалидация кеша** — сбросить ключ при изменении исходных данных
26. **Rate limiting** — не больше N запросов в минуту с IP/юзера
27. **Idempotency-key** — клиент шлёт уникальный заголовок, сервер возвращает тот же результат при повторе (защита от двойной оплаты)
28. **Retry с backoff** — повторять упавший запрос к внешнему API с возрастающей паузой
29. **Graceful shutdown** — по SIGTERM дослужить текущие запросы, потом выйти
30. **Аудит-лог** — таблица `audit_log` с `(who, what, when, before, after)`
31. **Версионирование API** — `/v1/...` и `/v2/...`, когда нужно сломать совместимость
32. **RBAC** — роли (admin, editor, viewer) и проверка «у роли есть permission X»
33. **Reset password** — токен на email, срок действия, одноразовость
34. **Email verification** — подтверди адрес по ссылке
35. **Refresh-токены** — короткий access + длинный refresh, ротация при использовании
36. **Хеширование паролей** — bcrypt/argon2, никогда не sha256
37. **Защита от SQL-injection** — только prepared statements, никаких `fmt.Sprintf` в SQL
38. **Optimistic locking** — колонка `version`, `UPDATE ... WHERE version = ?`, защита от двух одновременных правок
39. **Pessimistic locking** — `SELECT ... FOR UPDATE` внутри транзакции, чтобы никто не трогал строку, пока работаешь
40. **Фоновая задача в очереди** — отдать тяжёлую работу воркеру, не блокируя HTTP-запрос
41. **Cron-задача** — раз в час пересчитать агрегаты, разослать дайджест
42. **Отправка email** — интеграция с SES/SendGrid, шаблоны, очередь
43. **Импорт CSV/Excel** — пользователь загружает файл, парсим, валидируем построчно, отчёт об ошибках
44. **Экспорт CSV/Excel/PDF** — выгрузить таблицу с фильтрами
45. **Метрики Prometheus** — `http_request_duration_seconds`, `http_requests_total{status=...}`
46. **Сквозной request-id** — генерим на входе, прокидываем во все логи и во внешние вызовы
47. **Connection pool tuning** — выставить `max_open_conns` / `max_idle_conns` под нагрузку
48. **Webhooks: приём** — внешний сервис стучится к нам, проверяем HMAC-подпись
49. **Webhooks: отправка** — мы стучимся к клиенту, retry при 5xx, dead letter после N попыток
50. **Feature flags** — переключатель «фича включена для 10% юзеров», без редеплоя

## 51–100 — специализированное, не каждый бэкендер всё встретит

51. **Локализация (i18n)** — отдавать строки на языке юзера, плюрализация
52. **Multi-tenancy** — один сервис обслуживает много клиентов, данные изолированы (колонка `tenant_id` или схема на тенанта)
53. **Quota на тенанта** — «у этого клиента лимит 10к запросов/час, дальше 429»
54. **OAuth2 / OIDC** — «войти через Google/GitHub» без своих паролей
55. **SSO через SAML** — единый вход для сотрудников корпораций (B2B-продажа требует)
56. **2FA / TOTP** — одноразовый код из Google Authenticator
57. **CSRF-защита** — токен в форме, чтобы чужой сайт не отправил запрос от имени юзера (нужно при cookie-сессиях)
58. **XSS-эскейпинг** — экранировать пользовательский ввод при рендере HTML
59. **Распределённый лок** — Redis SET NX, чтобы из 5 инстансов сервиса только один взял задачу
60. **Outbox pattern** — пишем событие в таблицу `outbox` в той же транзакции, отдельный воркер потом доставляет в Kafka (надёжная публикация)
61. **Дедупликация** — записи приехали из разных источников, схлопнуть по бизнес-ключу
62. **Безопасный счётчик под нагрузкой** — лайки/остатки, атомарный `UPDATE ... SET count = count + 1` или Redis INCR
63. **Резервирование товара** — двое купили последний айтем одновременно, не дать обоим
64. **Биллинг-интеграция** (Stripe/ЮKassa) — создать customer, charge, webhook про успех/фейл
65. **Подписки и продления** — recurring billing, обработка отмены
66. **Возвраты (refunds)** — полные и частичные, как они отражаются в балансе
67. **Промокоды/скидки** — правила применения, лимиты использования
68. **Read-replicas** — отправлять SELECT'ы на реплику, INSERT/UPDATE на мастер
69. **Партиционирование** больших таблиц — разбить таблицу по дате/тенанту, чтобы запросы били только в нужную партицию
70. **Sharding** — данные не помещаются в одну БД, разносим по нескольким по ключу (юзер-id)
71. **CDC (Change Data Capture)** — Debezium читает WAL Postgres и публикует изменения в Kafka, чтобы другие сервисы реагировали
72. **Pub/Sub в Kafka/NATS/RabbitMQ** — сервис A публикует событие, сервис B подписан и реагирует
73. **Идемпотентный консьюмер** — то же событие пришло дважды (Kafka гарантирует at-least-once), обработать один раз
74. **Dead letter queue** — сообщения, упавшие N раз, отправляются в отдельную очередь для разбора
75. **Saga** — длинная операция через 3 сервиса (заказ → оплата → доставка), при падении середины — компенсирующие действия для отката
76. **Event sourcing** — храним не текущее состояние, а лог событий (`OrderCreated`, `ItemAdded`, `Paid`), состояние восстанавливаем проигрыванием
77. **Circuit breaker** — внешний сервис лежит, перестаём долбить его на 30 секунд, чтобы не плодить таймауты
78. **WebSockets** — двусторонний канал (чат, live-обновления)
79. **Server-Sent Events** — односторонний стрим сервер→клиент (нотификации, прогресс)
80. **Long polling** — клиент делает запрос, сервер держит до 30 сек, отвечает как только есть данные
81. **GraphQL-эндпоинт** — один URL вместо десятков REST, клиент сам пишет запрос с нужными полями
82. **gRPC-сервис** — RPC поверх HTTP/2, контракт описан в `.proto`-файле, клиент и сервер генерятся из схемы; типичная замена REST между внутренними сервисами
83. **OpenAPI/Swagger** — описание REST API в YAML, из него генерится дока и клиентские SDK
84. **Контрактные тесты** — проверка, что фронт и бэк согласованы по схеме (Pact)
85. **Юнит-тесты** — функция в изоляции, внешние зависимости замоканы
86. **Интеграционные тесты с реальной БД** — testcontainers поднимает Postgres в Docker на время теста
87. **E2E API-тесты** — сервис поднят целиком, тест дёргает HTTP извне
88. **Нагрузочные тесты** — k6/vegeta, замерить «сколько RPS держит до 500ms p99»
89. **Chaos-тесты** — намеренно убиваем pod / рвём сеть, проверяем, что сервис восстановится
90. **Профилирование** — в Go `pprof`, найти, какая функция жрёт CPU/память
91. **Утечка горутин** — запустили горутину и не дождались, она копится; ищется через `runtime.NumGoroutine` и pprof
92. **Утечка соединений** — забыли `defer rows.Close()`, пул БД исчерпался; ищется по метрикам пула
93. **CI/CD-пайплайн** — на PR прогон тестов и линтера, на merge в main — деплой
94. **Blue-green / canary деплой** — раскатить новую версию на 5% трафика, посмотреть метрики, потом на 100%
95. **Обратно-совместимая миграция** — новый код должен работать на старой схеме (потому что во время деплоя крутятся обе версии)
96. **Rollback** — откатить деплой не сломав данные (поэтому миграции делают добавляющими, а не удаляющими сразу)
97. **Бэкапы БД и проверка восстановления** — бэкап без regular restore-теста = нет бэкапа
98. **Секреты** — вынести пароли/ключи из кода в Vault/env, настроить ротацию
99. **Алерты на метрики** — если p99 latency > 500ms 5 минут подряд → дёрнуть дежурного в PagerDuty
100. **Геораспределение** — БД и сервисы в нескольких регионах, маршрутизация юзера в ближайший

# Go-специфичные навыки

Эти задачи плохо переносятся между языками: в Python (GIL) или Node (event loop) их формулируют иначе или они вообще не возникают. Каждый пункт — что значит **уметь** это на практике, а не «слышать термин».

## Конкурентность (фундамент языка)

1. **Ловить data race через `go test -race`** — запускать тесты и локальный сервер с флагом `-race`, читать вывод детектора (адрес памяти, кто пишет, кто читает, в каких горутинах), сводить проблему к конкретной строке. Понимать ограничение: детектор видит только реальные гонки в момент выполнения — нужны тесты, прогоняющие конкурентный путь.

2. **Выбирать защиту от гонки осознанно** — `sync.Mutex`/`RWMutex` для общего состояния со сложными инвариантами, `sync/atomic` для одиночных счётчиков/флагов, канал — когда логика естественно укладывается в pipeline. Не «везде Mutex».

3. **Находить утечки горутин в живом сервисе** — открыть `/debug/pprof/goroutine?debug=2`, увидеть, на чём именно зависли (receive из канала, который никто не закроет; Lock, который никто не отпустит; `time.Sleep` в бесконечном цикле без ctx-cancel). Чинить добавлением выхода по контексту или явного закрытия канала.

4. **Прокидывать `context.Context` сквозь все слои** — первым аргументом во все функции, ходящие в БД/сеть/RPC. Не хранить в полях структуры (контекст живёт по запросу, структура — дольше). Понимать, что отмена сверху должна доходить вниз, иначе после отвалившегося клиента сервер ещё минуту что-то считает.

5. **`WithTimeout`/`WithCancel` с обязательным `defer cancel()`** — забытый `cancel()` = утечка таймера и parent-контекста. `cancel()` нужен даже после успешного завершения.

6. **Закрывать каналы по правилу «только отправитель, и только один»** — send в закрытый канал паника, receive из закрытого = zero value + `ok=false`. Если отправителей несколько — координация через `sync.WaitGroup` + отдельный `done` канал, или `errgroup`.

7. **Писать `select` с отменой и таймаутом без утечки таймеров** — `case <-ctx.Done()` почти всегда обязателен. `time.After` в цикле течёт (создаёт новый Timer на каждый вызов, который не освобождается до срабатывания) — использовать `time.NewTimer` + `Stop()`.

8. **Реализовать worker pool с лимитом параллельности** — семафор через буферный канал размером N, или `errgroup.Group` + `SetLimit(N)`. Объяснять, почему не «горутина на каждый item» (взрыв памяти, контеншн на shared ресурсах).

9. **Использовать `errgroup` для fan-out с отменой при первой ошибке** — `g, ctx := errgroup.WithContext(parent)`; первая ошибка любого `g.Go()` отменяет общий ctx, `g.Wait()` возвращает её.

10. **Понимать ловушку замыкания над переменной цикла (до Go 1.22)** — `for _, v := range xs { go func(){ use(v) }() }` — все горутины видят одно `v`. Лечится `v := v` в начале цикла или передачей параметром. В 1.22+ починили в языке, но в legacy-коде встречается.

11. **Понимать ловушку typed nil интерфейса** — `var p *MyErr; return p` через сигнатуру `error` даёт интерфейс, который `!= nil` (потому что в интерфейсе хранится тип + значение, и тип не nil). Лечится явной проверкой и возвратом `nil`.

12. **Использовать `sync.Once`, `sync.Pool`, `sync.Map` по назначению** — `Once` для ленивой инициализации (один раз на процесс), `Pool` для переиспользования тяжёлых буферов (но объект может исчезнуть в любой момент!), `Map` только для специфичных паттернов (read-mostly или disjoint keys per goroutine) — иначе обычный `map`+`Mutex` быстрее.

## Ошибки

13. **Заворачивать через `%w`, распаковывать через `errors.Is` / `errors.As`** — `Is` для sentinel-значений (`sql.ErrNoRows`, `io.EOF`), `As` для типизированных. Знать, когда нужен sentinel, а когда тип с полями (`code`, `field`).

14. **Мапить ошибки на границе слоёв** — БД-ошибку (`pgx.ErrNoRows`) обернуть в доменную (`ErrUserNotFound`), на HTTP-уровне смапить в код (404/409/422). Наружу не отдавать `pq: duplicate key`.

15. **Защищать процесс через `recover` в HTTP middleware** — паника в одном хендлере не должна убивать весь сервер. Логировать стектрейс. В бизнес-логике паниковать самому нельзя.

## HTTP-сервер и клиент

16. **Выставлять таймауты на `http.Server`** — `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`. Дефолтный `http.ListenAndServe` без них уязвим к slowloris. Один из самых частых code-review комментариев.

17. **Делать graceful shutdown через `signal.NotifyContext`** — поймать SIGTERM/SIGINT, отменить ctx, `server.Shutdown(ctx)` с разумным таймаутом на дослуживание in-flight запросов.

18. **Переиспользовать `http.Client` с явными таймаутами** — не `http.DefaultClient` и не «клиент на каждый запрос». Настроить `Timeout` на клиенте + кастомный `Transport` с keep-alive и `MaxIdleConnsPerHost`.

19. **Закрывать `resp.Body` и дочитывать его до конца** — `defer resp.Body.Close()` сразу + `io.Copy(io.Discard, resp.Body)` если тело не нужно. Иначе keep-alive не переиспользует TCP-соединение.

20. **Прокидывать контекст в исходящий HTTP** — `http.NewRequestWithContext(ctx, ...)`, чтобы внешний вызов отменился вместе с входящим запросом.

21. **Парсить большие тела стримом** — `json.NewDecoder(r.Body).Decode(&v)` вместо `io.ReadAll + json.Unmarshal`. Разница в памяти на 100 МБ JSON — критична.

## Работа с БД

22. **Всегда использовать `*Context`-варианты** — `QueryContext`, `ExecContext`, `BeginTx(ctx, ...)`. Иначе запрос не прервётся по таймауту/cancel'у — и при отвалившемся клиенте будет долбить БД.

23. **Закрывать `rows`** — `defer rows.Close()` сразу после удачного `Query`. Забыли = утечка коннекта из пула, под нагрузкой получишь `pool exhausted`.

24. **Настраивать пул `database/sql`** — `SetMaxOpenConns`, `SetMaxIdleConns`, `SetConnMaxLifetime`. Дефолты подходят для hello-world, не для прода (особенно с pgbouncer перед БД).

25. **Писать транзакции с гарантированным rollback** — `tx, _ := db.BeginTx(ctx)`, сразу `defer tx.Rollback()` (no-op после успешного commit). Защищает от забытого rollback на ошибочной ветке.

26. **Выбирать SQL-обёртку под задачу** — голый `pgx` для контроля; `sqlx` для удобного маппинга в структуры; `sqlc` для типобезопасного кода из `.sql`-файлов; ORM (`ent`/`gorm`) только когда явно нужен.

## Тесты

27. **Писать table-driven тесты** — `for _, tc := range cases { t.Run(tc.name, ...) }`. Каноничный паттерн, без него ревью не пройдёт.

28. **Гонять `go test -race ./...` в CI** — обязательно. Замедляет в 5–10 раз, но иначе гонки уедут в прод.

29. **Тестировать HTTP через `httptest`** — `httptest.NewRecorder` для unit-уровня хендлера, `httptest.NewServer` когда нужен реальный сокет (для http-клиента под тестом).

30. **Поднимать реальные зависимости через testcontainers** — Postgres/Redis/Kafka в Docker на время теста вместо моков. Особенно для интеграций с БД и брокером.

31. **Писать бенчмарки и читать аллокации** — `func BenchmarkX(b *testing.B)`, `b.ReportAllocs()`, `go test -bench -benchmem -cpuprofile -memprofile`, разбирать через `go tool pprof`.

32. **Писать fuzz-тесты для парсеров и валидаторов** — `func FuzzX(f *testing.F)` + seed-corpus + `go test -fuzz`. Ловит крэши на неожиданном вводе.

## Сборка и эксплуатация

33. **Встраивать ассеты в бинарник через `go:embed`** — миграции, HTML-шаблоны, статика. Один файл на деплой.

34. **Кросс-компилировать под нужную платформу** — `GOOS=linux GOARCH=arm64 go build`. Главный козырь Go для деплоя.

35. **Собирать минимальный Docker-образ** — multi-stage Dockerfile с `FROM scratch` или `gcr.io/distroless/static`, образ 10–20 МБ вместо 800.

36. **Настраивать `golangci-lint`** — `.golangci.yml` с набором линтеров (`errcheck`, `gosec`, `govet`, `revive`, `gocritic`...). Без него ревью превращается в указание скобок.

37. **Использовать `go generate` для кодогенерации** — `sqlc` (SQL→Go), `mockgen` (моки интерфейсов), `oapi-codegen` (OpenAPI→handlers), `protoc-gen-go` (proto→Go).

38. **Выставлять `GOMAXPROCS` по CPU-лимиту контейнера** — подключить `go.uber.org/automaxprocs` (`import _ "..."`). Иначе Go видит все ядра ноды (например 64) и плодит контеншн на 1-CPU контейнере.

39. **Настраивать `GOMEMLIMIT`** — мягкий лимит памяти (Go 1.19+), GC начнёт работать активнее перед OOM. В k8s выставлять чуть ниже memory limit пода.

40. **Раскладывать проект через `cmd/` + `internal/`** — `cmd/<name>/main.go` для каждого бинарника, `internal/` для пакетов, которые не должны импортироваться извне (компилятор это форсит).

41. **Профилировать живой сервис через `net/http/pprof`** — подключить на отдельный приватный порт, снять `go tool pprof http://...:6060/debug/pprof/heap`, читать flame graph. Знать разницу `inuse_space` (что сейчас в памяти) vs `alloc_space` (что было выделено суммарно).

42. **Читать вывод escape analysis** — `go build -gcflags="-m"` показывает, какие переменные «сбежали» на heap. Применять, когда профайлер показал давление на GC.

43. **Логировать через `log/slog`** — стандартный структурный логгер (Go 1.21+). Уметь сделать кастомный handler, прокинуть request-id во все логи запроса через `slog.With(ctx, "request_id", id)`.
